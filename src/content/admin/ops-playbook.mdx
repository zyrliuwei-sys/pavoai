# 哥飞：让 AI 统计数据 → 读数据 → 做实验 → 选最赚钱的版本

> 哥飞原话（10-03）：「具体怎么做精细化运营，大家可以翻看从 9 月 28 日到今天我的所有发言。」
> 他的总原则（10-02）：「我的方法就是让 AI 去写代码，增强我们网站后台功能，而不是去接入第三方服务。」

整条链只有一个底座：**数据在自己的数据库里，代码是 AI 自己写的**。所以 AI 能「对照着自己写的代码看数据」，这是第三方统计工具做不到的。

---

## 第 1 步：让 AI 写数据统计代码

**做法（09-17 首次讲）**：不用第三方打点，让 AI 建一张**事件表**，记录用户从访客 → 注册 → 付费每个关键节点的行为日志。

自建的三个理由（哥飞原话压缩）：

1. AI 直接改代码上报数据很方便，集成第三方反而慢。
2. AI 能直接在数据库里把事件**关联到用户、订单、生成记录**，得到更细的各级转化数据；第三方「很难关联到具体的用户身上」。
3. 数据再拿给 AI 分析时，代码是它自己写的，它能对照代码去看数据，再改交互流程。

**具体要记哪些东西**（从截图还原）：

| 要素       | 怎么做                                                                                                                            | 出处  |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------- | ----- |
| 漏斗事件   | 上传照片 → 点生成 → 登录 → 看到付款弹窗 → 点了某个套餐 → 进 Stripe 付款页 → 付款                                                  | 10-10 |
| 首次来源   | 每个用户记录第一次来站的渠道（ChatGPT / Google / 直接 / 广告），一直跟到付款                                                      | 9-30  |
| 国家       | 按「第一次来访时的国家」记                                                                                                        | 10-10 |
| **版本号** | 每次构建把 git 提交号编进页面和服务端，每条事件都带构建号；访客归属「本时段第一次打开页面时的版本」，隔天在新版本回来也不会被挪走 | 9-17  |
| 实验组     | 每次弹窗展示记录是哪个实验版本                                                                                                    | 10-08 |
| 价格快照   | 用户多时，每次改价生成快照，注册时绑定价格快照 ID                                                                                 | 10-08 |

![0917_125411_message_5_3500](/imgs/ops-playbook/0917_125411_message_5_3500.jpg)
_AI 回复：「每次改动 = 一个版本，漏斗按版本分开看」。漏斗页有版本选择器 + 按版本对比表，版本名用提交说明而不是哈希。_

**口径坑（10-10 AI 自己踩的）**：用「实验版本的展示计数」会混进自己的测试和回访，改成**每一步的独立人数**才准。测试流量也要排除（10-03 AI 从结账页显示人民币/港币识别出是国内同行在测）。

## 第 2 步：让 AI 能读到统计的数据

数据在自己库里，AI 读数据有三种形态：

**① 一句话问数据**（不建看板也行）

> 哥飞：「看看今天的全站数据」→ Claude 跑 10 条命令，给出今日 vs 昨日同时段、按来源的付款率，结论「收入下降是访客少了，不是付款流程坏了」。

![1002_020307_message_5_4800](/imgs/ops-playbook/1002_020307_message_5_4800.jpg)

**② AI 写的看板**（10-02：「我的后台，也是 Claude 直接写的数据看板」）

- 他最喜欢的功能：**今天此时此刻收入多少 vs 昨天此时**（同时点对比，避免拿半天比全天）
- 五张卡片：今日已付 / 24h 未付款人数 / API 余额还能撑几小时 / 出片成功率（标红告警）/ 未处理工单

![1002_123053_message_5_4820](/imgs/ops-playbook/1002_123053_message_5_4820.jpg)

- 按渠道漏斗表，脚注写死口径：渠道 = 首次触达；活跃 = 生成过视频；排除测试账号；注册率 = 注册 ÷ 访客；付费率 = 付费 ÷ 注册

![0930_000706_message_5_4625](/imgs/ops-playbook/0930_000706_message_5_4625.jpg)
_结论：ChatGPT 来的 282 访客注册率 61%、付费率 6.4%；Google 自然流量注册 30%、付费 0。_

- 内页付费归因（9-29）：哪个内页带来的用户最终付费、首次生成到付费隔多久（平均约 6 分钟）

![0929_123445_message_5_4556](/imgs/ops-playbook/0929_123445_message_5_4556.png)

- 每日漏斗表：访客 / 注册 / 付费人数 / 订单 / 收入 / 访客→注册 / 访客→付费 / 注册→付费 / 访客人均付费 / 注册人均付费

![1003_111934_message_5_4870](/imgs/ops-playbook/1003_111934_message_5_4870.png)

**③ AI 每小时自动巡检**（「每小时一次的运营循环」）
报告内容：付款同比、几小时没新付款的告警、补单核对、出片成功率、API 余额够撑多久、各实验胜出概率和展示进度、ChatGPT 抓取了几次页面带来几次点击。

![1008_175548_message_5_5505](/imgs/ops-playbook/1008_175548_message_5_5505.jpg)

外加每笔付款实时推送（邮箱 / 注册时间 / 付款时间 / 国家 / 来源 / 关键词 / 是否升级补差价），一眼看出「ChatGPT 来、注册 3 分钟就付款」这类行为。

## 第 3 步：让 AI 基于数据分析决策，再写代码做实验

**分工**（10-08）：「我有一个大概的想法，然后就跟 Claude 去商量我们要怎么实现，然后他就会去实现，并且还给我做实验，一半流量用 A 方案，一半流量用 B 方案，看看哪个方案能够胜出。」
10-03：「有任何问题，直接跟 AI 说，让他去解决。」

**AI 从数据得出决策的案例：**

| 数据发现                                                                                                                                      | 决策 / 实验                                                              | 出处     |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | -------- |
| 邮箱登录用户占 13%，付费率 11.2%，高于 Google 登录的 6.9%                                                                                     | 不关邮箱登录                                                             | 10-03    |
| ChatGPT 访客在 Trio 套餐排第一时花得最多，其他人在月付排第一时花得最多                                                                        | 新增「按来源」版本，和三个原版本各分约 1/4 流量                          | 10-09    |
| 各国漏斗对比：欧洲看了价格不点（意大利 5-7% 点套餐，美国 26%）；拉美点了付不了（墨西哥到 Stripe 只 14% 付成功，美国 55%）；美国访客人均 $1.04 | 10-09 已上线「按来源和国家显示不同定价」；10-10 这份国家数据是之后的复核 | 10-09/10 |
| 站内付款 23 次只成交 2 单，跳转 Stripe 17 次成交 5 单                                                                                         | 提前停掉站内付款（收入优先），代码保留                                   | 10-02    |
| 新用户走完流程发现 5 个 bug（例如引导奖励被截断，只拿到 15 积分，一张图都出不了）                                                             | 修复并验证                                                               | 9-23     |

![1009_231320_message_5_5659](/imgs/ops-playbook/1009_231320_message_5_5659.jpg)

**AI 当分析员，人当质检员**：10-10 哥飞反驳 AI「那晚人变多了」的说法，AI 认错，改用独立人数对比三晚，把问题定位在「付款弹窗 → Stripe」这一步，最大嫌疑是「月付排第一给所有人」这个改动，并注明还不能 100% 定案。

## 第 4 步：让 AI 基于实验数据选每个模块用哪个版本

**结构**（10-10）：「每一个模块，我都有多种 UI，不同模块之间的连接也用了不同的 UX。然后就去做实验，看看哪个 UI，哪个 UX 效果好。」

### 具体案例：跳转 Stripe vs 站内内嵌 Stripe

_来源：2026-10-01 13:39，哥飞在群里发言「AI 帮我做 AB 测试」并附图。当时的状态是「Stripe 支付页已上线；站内内嵌 Stripe 代码已上线，实验还没开启」。_

![2026-10-14_stripe-ab-test](/imgs/ops-playbook/2026-10-14_stripe-ab-test.jpg)

**先把购买信息讲清楚。** 已上线的 Stripe 支付页做了四项调整：商品名下增加按买家语言显示的说明，解释买的是单曲、约几首的包还是月度套餐，套餐注明「积分永不过期」；增加示例视频截图；付款按钮旁写「生成失败不扣费，积分立即退回」，订阅另加「随时可取消」；删掉不总能成立的「高清」表述，因为用户也可以选择 480p。

这些改动分别回应「买到什么、效果如何、失败怎么办、订阅能否退出」。这是对改动目的的整理，截图没有提供它们各自提升转化的实验结果。

**再比较两种支付路径。** 截图明确写出的实验设计是：

| 项目     | 设计                                                                                   |
| -------- | -------------------------------------------------------------------------------------- |
| A 组     | 沿用跳转到 Stripe 页面付款的路径                                                       |
| B 组     | 留在本站付款页，一侧展示示例视频、购买说明和保证，另一侧是 Stripe 支付表单             |
| 流量分配 | 两边各 50%                                                                             |
| 观察门槛 | 直到两边各有 400 人看到                                                                |
| 判胜指标 | 按收入判胜负                                                                           |
| 保持一致 | 两边价格和付款方式完全一样                                                             |
| 防止丢单 | 内嵌会话创建失败时自动改用原来的 Stripe 页面；页面始终保留「改用 Stripe 页面付款」链接 |

这里测试的是**整套支付体验**：既改变是否跳转，也改变示例视频、说明和保证的展示方式。因此，即使一组胜出，也不能仅凭这个实验认定是「不跳转」这一项产生了效果。

**实验时间线：10-01 设计，10-02 提前停用。** 10-01 的截图记录了支付路径 A/B 测试的设计；次日记录显示，站内付款 23 次成交 2 单，跳转 Stripe 17 次成交 5 单，随后提前停掉站内付款、保留代码。因此，「每组 400 人看到」是原计划的观察门槛，不能写成已经跑满的样本量。

这个案例可借鉴的是：让 AI 把改动做成可分流、可记录、可回退的实验，再用实际收入决定去留。记录时还应明确「看到」按独立人数还是展示次数统计、收入归因的时间窗口，以及回退订单归属；这些是复用时需要补齐的口径，截图未交代。

**实验引擎规则**（从截图还原）：

- 实验变量：付款弹窗里套餐的排序、加购方案（trio）、地区价格（low_first）、弹窗提示和文案、页面的五个版本
- **弹窗实验的比较指标：每次弹窗展示带来的平均收入**（而不是转化率）；本次补充的支付路径实验只写明「按收入判胜负」，未说明是否使用同一人均口径
- 每版要达到预设观察量才下结论；本次支付路径截图明确为「两边各有 400 人看到」，其他实验另有每组 60 人等门槛，不混用人数与展示次数
- 之后系统**自动把更多流量给赚得多的版本**，但每版至少留一部分做对照（多臂老虎机思路）
- AI 每小时检查一次实验进度，报告胜出概率（例如 trio 0.75，进度 90/200）

**代价要认**（10-10）：「我一直在做实验，事实上导致一大部分流量都被浪费了……但不做实验，就不会知道最强配置是哪个。」
**风险要盯**（10-10）：改错一个交互，上午 12 小时只有 1 单 $9.9，第二天同时段 12 单 $147。所以同时点对比的看板必须有。

**实验里胜出的赚钱模块**（追加销售）：

- 免费额度只够最低模型，用户选高级模型时提示积分不足 → 付费（10-02）
- 结账页旁边推荐「$19.9 三个视频」，压过「$9.9 一个视频」（10-08）
- 付款后弹 Thank-you Deal：$1 一个视频，最少 20 个（10-08）
- **补差价升级**：今天已付的钱可以抵扣，同一用户一天能升级两次（$29 → $99）（10-02/10-08）
- 给付费老用户发邮件推新优惠（Resend）：208 封 → 6 人回站 → 2 人买（10-05）

## 哥飞自己踩的坑（直接避开）

1. **没让 AI 留实验日志**（10-09）：「我之前忘记让他把每一次他读到的数据、他的改进、他的实验，以及后面的对比结果保存起来」，导致写复盘时中间状态难以还原。→ 一开始就让 AI 维护一份实验日志：日期 / 读到的数据 / 假设 / 改动 commit / 结果。
2. 口径错误：展示计数混进测试和回访的人，要用独立人数。
3. 先做流量，再做精细化运营：数据量太小时对比没有意义（9-28）。他也嘲讽过先造一套自动运营系统、产品却没有用户的做法（9-30）。
